```

```

```
source .venv/bin/activate && python3 -m unittest test_panchangam_utils.TestFavorableNakshatrams.test_sample_input_uthiradam -v

```

## Architecture

`panchangam_utils.py` is a utility module modeling the 27 Hindu Nakshatras (lunar mansions) and, from there, finding favorable calendar days using live panchangam data.

### Core nakshatra model

- `NAKSHATRAS`: canonical ordered list (index 0 = Ashwini) of dicts with `Tamil`, `Sanskrit` (Devanagiri script), and `English` (romanized) names, sourced from https://www.drikpanchang.com/tutorials/nakshatra/nakshatra.html.
- `_LOOKUP` / `_build_lookup()`: a case-insensitive name → index map built once at import time from every value (Tamil/Sanskrit/English) in `NAKSHATRAS`, so any of the three naming systems can be used as input.
- `_ALIASES`: maps known alternate/inconsistent spellings (e.g. "uthiraadam") to the canonical lookup key, since Tamil nakshatra transliterations vary across sources.
- `resolve_nakshatra_index(nakshatra)`: resolves any Tamil/Sanskrit/English name (via `_LOOKUP`/`_ALIASES`) to its 0-based index in `NAKSHATRAS`. This is the shared primitive everything else builds on.
- `next_27_nakshatras(nakshatra)`: rotates `NAKSHATRAS` via modulo arithmetic so the given nakshatra becomes position 0.
- `favorable_nakshatrams(nakshatram)` / `favorable_nakshatram_indices(nakshatram)`: partition the 27 nakshatras into favorable/not-favorable using a fixed set of 1-based positions (`_FAVORABLE_POSITIONS`) — the classical 9-tara (Tarabala) cycle repeated three times across 27 nakshatras. Position 1 (the argument nakshatra itself, Janma tara) always lands in `not_favorable`. The `_indices` variant returns 0-based `NAKSHATRAS` indices instead of Tamil name strings, so favorability checks never depend on string-matching a nakshatra name.

### `fetch_favorable_month_days`: favorable-day lookup via drikpanchang.com

Given favorable weekdays, a person's nakshatram, a city, and a starting month, this scrapes drikpanchang.com's daily Tamil panchangam page for every matching weekday across a forward-looking window of months, and reports which of those days have a favorable nakshatra + Tamil Yogam (Siddha/Amrutha, not Marana).

- `resolve_geoname_id(city_name, chooser=None, interactive=True)`: resolves a city name to drikpanchang's `geoname-id` URL param **offline**, via the bundled `geonamescache` dataset (NOT `pgeocode` — that library only covers postal codes and has no `geonameid` field at all). Falls back through exact-name → substring-name → exact-alternate-name → substring-alternate-name matches.
  - **Does not silently guess when a name matches multiple distinct places** (e.g. "Springfield" matches 8+ US states) — picking the most populous match used to be the default and was found to be the wrong call for this feature (a user could easily mean the small/less-populous place). Instead: `city_name` can carry a `", state"` and/or `", country"` qualifier (by name or code, e.g. `"Springfield, IL"` or `"Springfield, Illinois, USA"`); if that doesn't fully resolve it, an explicit `chooser` callable (given the candidate list, returns the chosen one — for scripted/programmatic and test use) takes precedence, then interactive `input()` prompting if stdin is a real terminal, then `AmbiguousCityError` (a `ValueError` subclass, carries `.candidates`) as the final fallback. `fetch_favorable_month_days` exposes the same `city_chooser`/`interactive` params and threads them through.
  - geonamescache only bundles cities above a population threshold, so a qualifier can name a real place that simply isn't in the offline data (e.g. "Sunnyvale, TX" — only Sunnyvale, CA exists in this dataset). When a qualifier matches nothing but there was only ever one candidate for the base name, this is treated as "the qualified place probably isn't in our data," not a typo: it still returns that one candidate but emits a `warnings.warn(...)` saying the qualifier didn't match anything, rather than silently substituting a possibly-wrong place with no signal at all.
  - US states are matched by name via `geonamescache.get_us_states()`; other countries' admin1 codes (e.g. Canadian provinces) are opaque, unnamed codes in this dataset, so state/province-name disambiguation only works reliably for US states — non-US disambiguation should use the country qualifier instead (admin1 *code* matching still works if you happen to know the raw code).
- `_fetch_day_panchang_html(...)`: fetches (or reads from an on-disk cache under `panchang_cache/`, keyed by geoname-id + date, no TTL since published panchangam data never changes) one day's page. Accepts a `session` param (anything with `.get(...)`) so tests can inject a fake transport instead of hitting the network.
- **drikpanchang rate-limits/reCAPTCHA-blocks aggressive scraping** (empirically triggered around ~100-120 rapid sequential requests during development). A blocked response is detected (`_is_blocked_response`) and raises `DrikPanchangBlockedError` instead of being cached or mis-parsed — never write a blocked response to the cache. `_DEFAULT_REQUEST_DELAY_SECONDS` (2s) throttles live requests; a full 12-month run can still be 100+ requests, so expect it to take minutes on a cold cache.
- `_parse_day_panchang(html, query_date)`: parses the `Nakshathram` and `Tamil Yoga` panchang elements into **independent, arbitrary-length segment lists** (`_nakshatram_segments`, `_tam_yogam_segments`), each a list of `(value, cutoff_or_None)` pairs where only the last entry has `cutoff=None`. This generality is load-bearing, not speculative: real data has shown up to 2 same-day Nakshathram transitions and 3 same-day Tamil Yoga transitions, and the two do **not** share transition times or transition counts (e.g. a nakshatra can span the entire day while Tamil Yogam still changes twice within it) — do not reintroduce a "primary/secondary" pair as the source of truth for favorability; that was tried and found to silently give wrong answers on real dates. `primary_nakshatram_for_the_day` / `secondary_nakshatram_of_the_day` / `primary_tam_yogam_for_the_day` / `secondary_tam_yogam_of_the_day` in the returned dict are just segments `[0]`/`[1]` for informational/API purposes.
  - Nakshatra names are resolved via drikpanchang's `<a title="next X (N)">` attribute (`N` = the standard 1-based nakshatra index) rather than by string-matching the visible text, because drikpanchang's own Tamil-page transliterations (e.g. "Mirugasirisham", "Magam", "Sathayam") differ from this file's canonical `NAKSHATRAS` spellings.
  - **`_parse_nakshathram_segments` and `_parse_tamil_yoga_segments` are deliberately NOT the same function**, because drikpanchang renders same-day transitions differently for the two: Tamil Yoga always gets an explicit, open-ended, no-"upto" trailing `<p>` for whatever comes after the last cutoff (so reading each `<p>` in document order is sufficient). Nakshathram almost never does — in the vast majority of real days (measured: 102/120 in a Chennai sample), there is exactly **one** `<p>` for Nakshathram even when it has a same-day cutoff, and the nakshatra that follows the cutoff is only recoverable by decrementing that same element's own `title="next X (N)"` index (current = N−1, next = N). A prior version of this code used one generic segment-parser for both and silently treated every single-element same-day-cutoff Nakshathram as if it lasted the entire day — this passed 120/120 cached-fixture checks (because the checks were written against that same buggy output) but produced wrong `"Entire day"` / `"from {time} onwards"` results for real users on ~85% of days. If you ever unify these two parsers again, re-derive the expected values independently (e.g. against a second, unrelated implementation or manual date-table cross-check) rather than trusting round-trip agreement with the code under test.
  - **Both `_parse_*_segments` functions must check `_crosses_into_next_calendar_day` on every segment, not just Nakshathram's.** A later bug had `_parse_tamil_yoga_segments` skip that check entirely, so whenever Tamil Yoga's first segment's "upto" fell after midnight (e.g. "upto 12:19 AM, Oct 18" when querying Oct 17), the code wrongly read the *next day's* Tamil Yogam value out of the following `<p>` and applied it to the rest of *today*, splitting what should have been a favorable "Entire day" into a bogus "until 12:19 AM". Each `_parse_*_segments` function now returns `(segments, next_day_continuation)`, where the latter is the actual cutoff time on the following day when the day's last segment is known (from a real "upto ... crosses midnight" fact, not silence) to hold until — surfaced by `_build_favorable_entry` as `"... (favorable until {next day's date} {time})"` on whichever trailing window reaches day-end.
- `_favorable_windows(day_result, favorable_indices)`: the actual favorability logic. Builds a timeline of the day cut at every cutoff time present in *either* segment list, evaluates favorability of the active nakshatra+yogam pair in each resulting slice, and merges adjacent favorable slices — correctly handling any number of transitions in either dimension.
- `_build_favorable_entry(...)`: renders the merged windows as `"{date} - Entire day"`, `"{date} - until {time}"`, `"{date} - from {time} onwards"`, or (rare, only possible with 2+ independent transitions in one day) a `"; "`-joined combination of these — or `None` if the day isn't favorable at all. Whenever a trailing window reaches day-end AND the underlying data shows it actually continues into the next calendar day until a known time (see `_next_day_continuation_label`), that's appended as `" (favorable until {date} {time})"` — don't drop this: a bare "Entire day"/"from {time} onwards" throws away real information that was visible in the raw page (a user caught this by comparing the label against drikpanchang's own "upto {time}, {next day}" text).
- `person` is **mandatory** (no default) and `output_dir` is optional: results are *always* additionally written to `{output_dir}/{slugified person}/{slugified city}/{Month}_{Year}.txt`, one file per forward-looking month (via `_write_month_file`/`_format_month_file_contents`), and each returned month dict gets an `"output_file"` path. `person` is passed through `_slugify_person_name` for that subfolder, which strips everything but `[A-Za-z0-9_-]` (spaces → underscores) specifically so a crafted name can't escape `output_dir` via `/` or `..` — don't bypass that sanitization when writing paths from `person`.
  - The `{slugified city}` level comes from `input_city_name` via `_slugify_city_name` (same sanitizer, so `"Springfield, IL"` → `Springfield_IL`, `"../x"` can't escape the person folder); `_person_city_output_dir` builds and creates `{output_dir}/{person}/{city}` and is the single place both `_write_month_file` and `collate_and_save_predictions` get their directory from. It exists because neither the `.txt` nor the `.json` file name carries the city, so when results lived directly under `{output_dir}/{person}/`, running the same person/month for a second city (e.g. Chennai, then Sunnyvale) silently overwrote the first city's results. The folder uses the city string *as the caller passed it* (not the geonames-resolved name), so `"Sunnyvale"` and `"Sunnyvale, CA"` land in different folders even though they resolve to the same place. `fetch_favorable_month_days` slugifies the city up front so an unusable city name fails before any network requests.
  - If `output_dir` isn't given, it defaults to `f"{person}_output_dir"` (the *raw*, unsanitized `person` string with the literal suffix `"output_dir"` appended — no separator, per explicit user request), a path relative to the current working directory at call time. This default is intentionally unsanitized (unlike the `person`-derived subfolder inside it) since it mirrors how an explicitly-passed `output_dir` also isn't sanitized — a `person` value with `/` in it would create nested directories in this default path, same as it would in any user-supplied path.
  - `person` being mandatory means `fetch_favorable_month_days(...)` now **always** writes files as a side effect — every call site (including tests) must account for this. Tests that don't care about the written files still need a real `person=` and normally an `output_dir=<tempfile.TemporaryDirectory()>` too, or they'll write into whatever the current working directory happens to be when the suite runs.
- **`person` is keyword-only, immediately after `forward_looking_months` in the signature, and required; every other parameter after it (`output_dir`, `use_cache`, `cache_dir`, `request_delay_seconds`, `session`, `city_chooser`, `interactive`) is keyword-only too** (the signature has a bare `*` right after `forward_looking_months=12`, then `person` with no default). `person` can't be a plain required positional parameter placed right after `forward_looking_months`, because `forward_looking_months` has a default value and Python doesn't allow a required parameter to follow a defaulted one in the same positional group (`SyntaxError: non-default argument follows default argument`) — keyword-only sidesteps that while still making `person` mandatory (Python raises `TypeError` if it's omitted) and keeping it textually right after `forward_looking_months`.
  - This keyword-only-everything design exists because of a real user bug: `person`/`output_dir` were first added positionally at the end of the parameter list (to avoid breaking `forward_looking_months`'s established positional usage), but a user naturally called `fetch_favorable_month_days(days, nakshatram, city, month_year, 1, "sreenaath", "output_results")` expecting positions 6/7 to be `person`/`output_dir` — they actually bound to `use_cache`/`cache_dir`, so `"output_results"` silently became the *drikpanchang HTML cache directory* instead of the output folder, with no error and no `person`-named subfolder ever created. Requiring `person` as keyword-only makes that same call raise a clear `TypeError` instead. If you add more parameters here, keep them keyword-only too.
- `collate_and_save_predictions(person, input_nakshatram, input_city_name, starting_month_year, forward_looking_months, output_dir, favorable_days_with_ts)`: called automatically by `fetch_favorable_month_days` right after all per-month `.txt` files are written (and by `main()`, transitively, via that same call), it reshapes the already-computed `favorable_days_with_ts` list into one consolidated JSON document — `{"person", "input_nakshatram", "input_city_name", "starting_month_year", "forward_looking_months", "months": [{"month", "year", "favorable_days": [{"date", "prediction"}, ...]}, ...]}` — and writes it to `{output_dir}/{slugified person}/{slugified city}/{slugified person}_{slugified starting_month_year}_{forward_looking_months}.json` (same per-person, per-city subfolder as the monthly `.txt` files). `_split_favorable_entry_into_row` turns each `"{date} - {prediction}"` display string from `_build_favorable_entry` into that `{date, prediction}` row via a plain `.partition(" - ")` — lossless because every such string has exactly that shape (see `_build_favorable_entry`'s docstring) — including semicolon-joined multi-window entries, which are kept as one unsplit `prediction` value rather than further decomposed. Every returned month dict also gets a `"consolidated_output_file"` key (same path, repeated per month, mirroring how `"output_file"` already works per-month). `_slugify_for_filename` is the generic sanitizer this, `_slugify_person_name` and `_slugify_city_name` all build on (spaces → underscores, everything outside `[A-Za-z0-9_-]` stripped) — the *filename* uses sanitized components, but the JSON's own `"person"`/`"starting_month_year"` fields keep the original, unsanitized values.

### CLI: `python3 panchangam_utils.py ...`

`_build_arg_parser()` (an `argparse.ArgumentParser`) and `main(argv=None)` at the bottom of the file expose `fetch_favorable_month_days` from the command line; `if __name__ == "__main__": sys.exit(main())` makes the file directly runnable. Positional CLI args mirror the function's required parameters in order — `WEEKDAY [WEEKDAY ...] input_nakshatram input_city_name starting_month_year person` (note `fav_days_of_week` uses `nargs="+"`, which argparse correctly reserves the trailing fixed positions for even when multiple weekdays are given, e.g. `Monday Wednesday Friday Uthiradam Chennai "Sept 2026" Sreenaath`) — everything else is an optional `--flag` mirroring a keyword-only parameter (`--forward-looking-months`, `--output-dir`, `--cache-dir`, `--no-cache`, `--request-delay-seconds`, `--non-interactive`). `session` and `city_chooser` aren't exposed (not meaningful/expressible from a shell); leaving `interactive` at its default is the CLI's equivalent of `city_chooser` — an ambiguous city name prompts interactively at the terminal instead.

`main()` catches `ValueError` (which also catches `AmbiguousCityError`, a subclass) and `DrikPanchangBlockedError` around the `fetch_favorable_month_days` call, prints `f"Error: {exc}"` to stderr, and returns exit code 1 — deliberately not a bare `except Exception`, so a genuine bug still surfaces as a full traceback rather than being swallowed into a generic CLI error message. On success it prints a per-month summary to stdout and the path each month was saved to (from the `"output_file"` key), then returns 0.

### Testing strategy for the scraper

`tests_fixtures/` holds small trimmed-down real drikpanchang HTML fragments (just the `.dpDayPanchangWrapper` subtree) captured during development, covering every parsing case found in real data (see filenames), plus one hand-crafted fixture (`synthetic_multi_window.html`) for a disjoint-favorable-windows case not yet observed live, and a minimal captcha page fixture. `TestParseDayPanchangFixtures` and `TestFetchFavorableMonthDaysIntegration` (via a fake `_FixtureSession`) run against these offline/deterministically. `TestFetchFavorableMonthDaysLiveSmoke` makes a handful of genuine live requests against drikpanchang.com and **skips itself** (doesn't fail) on network errors or a `DrikPanchangBlockedError`, since it depends on a third-party site. Prefer extending the fixture-based tests for new parsing edge cases; reserve live requests for smoke-testing that the real site still matches this module's assumptions.

Every `fetch_favorable_month_days(...)` call in the test suite passes both `person=` and (except for the tests specifically about the default) an explicit `output_dir=<tempfile.TemporaryDirectory()>`, since `person` is mandatory and a call now always writes files as a side effect — omitting `output_dir` in a test would write into whatever directory the suite happens to run from. The handful of tests that specifically verify the *default* `output_dir` behavior (`f"{person}_output_dir"`, relative to cwd) use `os.chdir()` into a temp directory for the duration of the call, restoring the original cwd in a `finally` block, so they don't pollute the real project directory either.

CLI coverage is split three ways: `TestArgParser` tests `_build_arg_parser()` directly (pure argparse wiring, no I/O); `TestMainFunction` calls `pu.main(argv)` in-process (capturing stdout via `contextlib.redirect_stdout`) against the real on-disk `panchang_cache/` (which already has Chennai's January 2026 fully cached from earlier development, so these run offline — `main()` has no `session` param to inject a fake one, unlike `fetch_favorable_month_days` itself); `TestCliSubprocess` actually shells out via `subprocess.run([sys.executable, str(script_path), ...])` for a handful of true end-to-end checks (help text, success path, error exit code), also relying on that same real cache to avoid live requests. `TestFetchFavorableMonthDaysDirectInvocation` is a dedicated (if largely redundant with the rest of the suite) test emphasizing the "import and call directly from another script" usage path specifically.

When adding new nakshatra-derived utilities, build on `resolve_nakshatra_index`/`next_27_nakshatras` for ordering/rotation rather than re-deriving indices, and accept input in any of Tamil/Sanskrit/English via the existing `_LOOKUP` mechanism.

## Group / couple favorable times (`find_common_favorable_times`)

`find_common_favorable_times(people, starting_month_year, forward_looking_months=3, *, group_name=None, output_dir=None, ...)`
(CLI: `panchangam_utils.py group --person 'NAME;NAKSHATRAM;CITY;WEEKDAY,...' --person ... "Month Year"`)
finds moments favorable for **every** person at once, where people may live in different cities or time zones:

- Each person is evaluated exactly like `fetch_favorable_month_days`, in their **own** city: only their own favorable weekdays (by local date), `_favorable_windows` against *their* favorable-nakshatram set, and yogam as published for their city. `_favorable_intervals` is the machine form of `_build_favorable_entry`: minute offsets from local midnight, with a window that runs to midnight extended past 1440 to the "(favorable until …)" next-day cutoff.
- Intervals are converted to UTC with `_local_minutes_to_utc`. The time zone comes from geonamescache's `timezone` field via `_city_timezone`, and wall-clock times are localised with `zoneinfo`, so DST is handled. Each person's intervals are `_merge_intervals`'d, then all people are `_intersect_intervals`'d. Nakshatram transitions are the same instant worldwide, so any overlap is automatically in a nakshatram favorable to all.
- Dates are scanned one day past each end of the window, so overlaps straddling the window edge across time zones aren't lost. An overlap is kept if it starts inside the window on *any* member's local calendar, and is bucketed by the first member's local start month.
- Output: `{output_dir}/{A}_{B}/{A}_{B}_{starting_month_year}_{N}.json` + `.txt`, with `output_dir` defaulting to `{A}_{B}_output_dir`. The JSON holds `participants` (with `timezone`), `common_favorable_nakshatrams`, and `months[].common_windows[]` of `{start_utc, end_utc, duration_minutes, local_times[{person, input_city_name, timezone, start, end}]}`.

Tests: `TestGroupIntervalHelpers`, `TestFindCommonFavorableTimes` (offline, over the Sunnyvale September 2026 fixtures) and `TestGroupCli`.

## Panchang data sources: drikpanchang.com + prokerala.com fallback

`fetch_day_panchang(geoname_id, day_date, *, sources=DEFAULT_PANCHANG_SOURCES, ..., unavailable_sources=None)` is the top-level, source-agnostic day lookup that `fetch_favorable_month_days` and `find_common_favorable_times` both call. It returns the `_parse_day_panchang`-shaped `day_result` plus a `"source"` key.

- **Order and fallback:** it tries each source in order, drikpanchang.com (`DRIKPANCHANG`) then prokerala.com (`PROKERALA`), each from cache first and then live. A `DrikPanchangBlockedError` (including its subclass `PanchangSourceBlockedError`) or a `requests.RequestException` moves on to the next source. When every source fails, it raises `PanchangSourceBlockedError`.
- **Blocked sources:** `unavailable_sources` is a per-run set. A source that gets blocked is not retried live for the rest of that run, though its cached pages are still used.
- **Cache files:** drikpanchang pages are cached as `{gid}_{YYYYMMDD}.html`, unchanged; prokerala pages as `{gid}_{YYYYMMDD}.prokerala.html` in the same directory.
- **Reporting fallbacks:** callers record which days fell back. Individual runs store this in the month dicts and JSON as `data_sources: {days_by_source, fallback_dates}`; group JSON stores `data_sources.fallback_dates`. The CLI prints a note, and `--no-fallback` restricts sources to drikpanchang only.
- **The prokerala parser:** `_parse_prokerala_day_panchang` produces the same segment and continuation shape as the drikpanchang parser.
  - Nakshatrams come from `.panchang-data-nakshatra`: dated ranges, identified by link slug via `_PROKERALA_NAKSHATRA_SLUGS`, and clipped to the calendar day.
  - Tamil Yogam comes from `.panchang-data-tamil-yoga`, **not** `.panchang-data-yoga` (the nithya yogam). Its cutoffs have no date: a cutoff before the page's sunrise is on the next day.
  - Unlike drikpanchang, prokerala always knows when the day's last nakshatram ends, so its `_nakshatram_next_day_continuation` is often set where drikpanchang's is `None`.
- **Known disagreement:** the sites use different weekday × nakshatram Tamil Yogam tables on some days. `TestSourceAgreement` pins these in `KNOWN_TAMIL_YOGAM_DISAGREEMENTS` (4 of 21 captured days, each flipping favorability), and asserts that nakshatram segments agree on all days. Fixtures are in `tests_fixtures/prokerala/{gid}_{YYYY-MM-DD}.html`.
